【背景】

T003 - Citation Evidence Grounding
优先级：P0
依赖：无
----------------------------------------------------------------------

【背景】
当前 snippet 是 query-aware，而不是 claim-aware；且现有 build_context 逻辑可能优先使用 b 而让 fb/full_body 不参与定位。

修改：
server.py / epistemic.py / 后续 context_builder.py

【具体实现】

1. fb/full_body

- 中文句界
- 英文句界

- [ ] full_body 优先于 body。
- [ ] span 在原始文本中可程序验证。
- [ ] 找不到 span 时 citation 不通过。
- [ ] 返回 start/end offset。
- [ ] 可生成完整语义 snippet 而不是生硬定长截断。

【测试】

新闻/公众号/网页正文可能包含类似 prompt 或“忽略之前指令”的文字。Retrieved text 必须永远被当 DATA。

【目标】
防止知识库文本控制 Agent 行为，同时保留文本本身作为分析对象。

【修改范围】
新增：
qa-backend/content_safety.py

metadata flags：
prompt_like_text
instruction_like_text
suspicious_markup
marketing_hype

【实现要求】
1. System prompt 明确 retrieved documents = untrusted evidence data。
2. 文档中出现“调用工具”“忽略系统”等文字不能影响 Tool Controller。
3. Context builder 用清晰边界包装证据块。
4. 不需要因为 prompt-like text 自动删除整条证据；它可能是研究对象。
5. Agent 只能从 orchestrator/system 定义的工具集合中调用工具。
6. trace 保存 risk flags。
7. 若未来 corpus 有 ACL/私有数据，权限过滤必须发生在候选进入 Agent 之前；当前公共 Tech-DB 可先保留接口。

【Definition of Done】
- [ ] prompt injection 测试文档不能改变 system behavior。
- [ ] retrieved document 不能自行要求 Agent 调用工具。
- [ ] 风险文本仍能作为普通内容引用/分析。
- [ ] risk flags 进入 trace。
- [ ] 有自动安全测试。

T008 - Probabilistic Provenance Clustering / 同源证据识别
优先级：P0
依赖：T007
----------------------------------------------------------------------

【背景】
多家媒体转载同一个原始新闻时，文档数量不代表证据独立性。现实转载可能改标题、改顺序、加入少量评论，因此不能只用 exact duplicate，也不能声称 100% 确定来源血缘。

【目标】
建立概率式 provenance clustering，识别“可能同源”的内容，让在线系统统计 independent evidence groups，而不是 document count。

【输入特征】
- canonical URL
- original URL
- redirect/source link
- domain
- explicit citation links
- title normalized similarity
- body text similarity
- embedding similarity
- publish/event time difference
- entity overlap
- existing event cluster
- source attribution phrase

【输出】
same_origin_probability
provenance_root_id
independent_group_id
provenance_confidence
provenance_reason/features

【实现要求】
1. 使用确定性特征 + 相似度模型组合。
2. 阈值配置化：
   - high confidence -> 合并 provenance group
   - ambiguous band -> uncertain，不强制合并
   - low -> independent candidate
3. existing dedup / cluster 作为 feature，不直接等同 provenance。
4. 后续 Evidence Grader 的独立证据数以 independent_group_id 为主。
5. 一个二手文章即使基于原始报道，也可能包含独立采访/新增数据；后续允许 claim-level provenance 扩展，第一版至少不要整篇一刀切成绝对同源。
6. trace 输出某候选被判重复来源的原因。

【Definition of Done】
- [ ] 明显全文转载能聚为同组。
- [ ] 改标题但正文高度相似的转载能聚为同组。
- [ ] 独立报道同一事件不会仅因为主题相同全部合并。
- [ ] ambiguous case 保留 probability。
- [ ] Evidence Selector/Grader 可读取 independent_group_id。
- [ ] 5 篇同源转载不会在独立证据计数中记为 5。

【测试】
建立小样本：
A. 5 篇同源转载
B. 3 篇独立采访同一事件
C. 1 篇转载但新增独立测试数据
检查 group 与 uncertain 情况。

T009 - Claim-aware Source Suitability
优先级：P1
依赖：T007, T008
----------------------------------------------------------------------

【背景】
“nvidia.com = 0.95”这类绝对来源分数会制造偏见与虚假精确度。同一个来源对不同 claim 的证明力不同。

【目标】
判断“这个来源对当前 claim 的证据角色和适配程度”，而不是判断“这个网站有多可信”。

【Source Type 至少支持】
standards_body
regulator
government
academic_primary
academic_secondary
company_technical_doc
company_press_release
research_institution
major_media
industry_media
secondary_repost
social_media
unknown

【Claim Type 可逐步支持】
product_spec
company_action
performance_claim
scientific_result
market_size
policy
prediction
opinion
historical_event
comparison
etc.

【输出】
source_suitability
evidence_role
attribution_required
independence_penalty
reason

【例子】
公司官方规格页：
- “该公司官方公布型号 X 带宽 1.8TB/s” -> 高适配，一手。
- “该产品实际比竞品快 3 倍” -> 只能支持“公司声称”，不算独立验证。

【实现要求】
1. Source prior 可配置，但不能直接决定 truth。
2. claim + source type + evidence role 联合判断。
3. 对 REPORTED_CLAIM / PREDICTION / OPINION 保留 attribution。
4. 不显示给用户“可信度 93%”。
5. Evidence Selector 使用 suitability 作为一个 feature，而非硬过滤。
6. Source Suitability policy 必须有 policy_version、规则来源/说明、claim-type applicability 与 calibration report；人工 override 可审计。

【Definition of Done】
- [ ] 同一来源对不同 claim 可得到不同 evidence role/suitability。
- [ ] 厂商性能自述不会自动升级为 independent fact。
- [ ] 规则/权重配置化。
- [ ] 有来源类型未知时安全 fallback。
- [ ] 有单元测试覆盖官方规格 vs 官方营销性能声称。

T010 - Temporal Metadata / 时间与版本感知
优先级：P0
依赖：T007
----------------------------------------------------------------------

【背景】
发布时间、事件时间、预测目标时间、事实有效时间不是同一件事。旧路线图与新正式发布可能都在库里，如果用户问“现在”，不能不区分版本。

【目标】
建立足够支持 current / historical / trend / superseded reasoning 的 temporal metadata。

【修改范围】
新增建议：
scripts/enrich_temporal_metadata.py
qa-backend/temporal.py

【字段】
published_at
event_time_start
event_time_end
target_future_time
valid_from
valid_to
supersedes
superseded_by
temporal_status:
  current
  historical
  superseded
  future_prediction
  unknown

【实现要求】
1. 明确区分 published_at 与 event_at。
2. 对“预计 2028 年”记录 target_future_time，而不是把发布时间当成结果发生时间。
3. Router 输出 temporal_intent：
   current / latest / as_of / historical / trend / unspecified
4. current/latest 查询中 superseded 证据降权或仅作为历史背景。
5. historical/trend 问题保留旧证据。
6. conflict detector 能把“旧计划 vs 新结果”识别为 VERSION_UPDATE。
7. 时间无法确定时标 unknown，不让 LLM随意补日期。
8. 非确定性 temporal extraction 必须保存 evidence locator / extraction_method / confidence；关键 current/as-of 判断不能只靠无证据的 LLM 日期推断。
8. answer 可选显示“基于知识库更新到某日期/版本”，防止用户把数据库覆盖范围误当世界实时状态。

【Definition of Done】
- [ ] current 查询不会优先拿明显 superseded 的旧资料作现状答案。
- [ ] historical 查询能正确使用旧资料。
- [ ] future prediction 与已发生事实有类型区分。
- [ ] temporal metadata 进入 Selector / Grader / Conflict Detector。
- [ ] 有 as-of date 测试。

【测试】
准备：
2024 roadmap：计划 2026 推出 A
2026 release：实际推出 B
测试：
“2024 年当时计划什么？”
“现在正式推出什么？”
“这个规划后来实现了吗？”

T011 - Entity Identity / Resolution V2（Umbrella Epic）
优先级：P0
依赖：T007
----------------------------------------------------------------------

【背景】
实体对齐不能简化成“加一个 alias 字典”。字符串 name 不能继续作为长期 node identity；false merge 会制造虚假的跨实体关系并污染 Graph Retrieval。

【目标】
建立 EntityMention -> Candidate Generation -> ResolutionDecision -> CanonicalEntity(stable opaque entity_id) -> CanonicalRelation。

核心要求：mention != entity；canonical_name 可变但 ID 稳定；alias 一对多；resolver 支持 LINK/NEW/AMBIGUOUS/BLOCKED；所有自动/人工 link、merge、split 可审计、可回滚；relation 先绑定 mention endpoint，再 materialize canonical relation；query-time 复用同一 resolver；生产通过 shadow -> partial -> full Graph-V2 渐进切换。

【详细执行】
本 Ticket 是 parent epic。必须执行后文 PART 2A - ENTITY IDENTITY / RESOLUTION V2 DETAILED WORKSTREAM 中 ER-001 ... ER-124。

【Definition of Done】
- [ ] mention != entity。
- [ ] stable opaque entity_id；rename 后 ID 不变。
- [ ] alias 一对多，ambiguous alias 不强制 merge。
- [ ] ontology/granularity policy versioned。
- [ ] deterministic fast path + Top-N + constrained LLM adjudication。
- [ ] resolver 支持 NEW / AMBIGUOUS / BLOCKED。
- [ ] false merge / missed merge / auto-link precision 有指标。
- [ ] manual override、merge/split、audit、rollback 完整。
- [ ] raw relation endpoint 使用 mention IDs；canonical edge 使用 stable entity IDs。
- [ ] query resolver 不以全图 substring scan 为主路径。
- [ ] identity snapshot atomic publish / rollback。
- [ ] shadow/partial/full activation 完整。
- [ ] ER-001 ... ER-124 全部满足各自 DoD。

----------------------------------------------------------------------
T027 - Evidence-grounded Semantic Knowledge Graph / Graph Pipeline 统一
优先级：P0/P1
依赖：T011, T003, T010, T012, T028, T044
----------------------------------------------------------------------

【背景】
当前 Graph 路最大的结构性问题不是“0.35 应该调成多少”，而是图里的边本身缺少足够严格的语义、方向和证据约束。
Legacy / fast graph 可以把实体共现建成弱边用于关联发现，但“共同出现”不等于存在明确语义关系。若 LLM 在建图时凭预训练知识补出原文没有支持的关系，Graph Retriever 随后沿这条边检索，就会把模型常识污染成数据库证据。

【目标】
把 Graph 升级为 evidence-grounded、typed、directional、temporal 的 Semantic Graph；保留 RELATED_CO_OCCURRENCE 作为弱关系。

【强语义关系示例】
RELEASED / DEVELOPED / USES / USES_MATERIAL / SUPPORTS / PART_OF /
COMPETES_WITH / ACHIEVES / IMPROVES / REPLACES / SUPERSEDES /
PARTNERED_WITH / INVESTED_IN / MEASURED_AT

【Edge Schema】
edge_id
subject_entity_id
predicate
object_entity_id / object_value
directional
record_id
evidence_span
evidence_start
evidence_end
extraction_confidence
grounding_status
source_role
published_at
valid_from
valid_to
extraction_method
graph_version

【建图输入】
优先 original full_body / grounded chunks；title/section 只作上下文。
synthetic_summary 不得作为唯一关系依据；模型领域常识不得形成无来源 production edge。

【关系抽取流程】
Original source -> Entity Resolution -> Relation Extraction -> Evidence Span Localization
-> Deterministic Exact-span Validation -> Optional independent semantic verification -> Edge creation

【硬规则】
1. production semantic edge 必须有 record_id。
2. 必须有 exact evidence span 或可验证的 coreference-grounded span。
3. 没有原文证据的关系不得进入 high-confidence semantic graph。
4. 关系方向必须保留；Company --USES--> Technology 不等于 Technology --USES--> Company。
5. 只有明确 symmetric predicate 才可双向查询。
6. LLM 自报 confidence 不能替代 deterministic grounding。
7. co-occurrence edge 必须明确标为 weak。
8. edge 可有多个 evidence refs / provenance groups。
9. 版本变化用 valid_from/valid_to/supersedes 表达，不无痕覆盖旧关系。
10. current fast graph 可保留为 legacy/fallback 直至 benchmark 决定迁移。

【节点类型】
organization / product / technology / material / standard / metric /
project / institution / person / location
不能所有节点统一成“概念”。

【Graph Pipeline 统一】
比较：
- current fast co-occurrence graph
- evidence-grounded semantic graph
- LightRAG graph/mix benchmark candidate

在线 Agent 仍通过可控 search_graph/search_hybrid interface 使用图谱，不绑死 rag.aquery()。

【Definition of Done】
- [ ] 每条 production semantic edge 有 record_id + exact evidence span。
- [ ] 没有 exact evidence 的 LLM relation 不进入高置信 semantic graph。
- [ ] predicate 与方向被保存。
- [ ] semantic edge 不再无条件 A<->B 双向化。
- [ ] co-occurrence 与 semantic relation 区分。
- [ ] 节点实体类型被保留。
- [ ] 同一 relation 可保留多 evidence refs。
- [ ] temporal/version metadata 可关联 edge。
- [ ] synthetic summary 无法独立生成 production semantic edge。
- [ ] canonical graph build pipeline/version 明确。
- [ ] current fast graph / semantic graph / LightRAG 有统一 benchmark。

T039 - Relation-aware Graph Retriever / 路径感知 Graph Ranking
优先级：P0
依赖：T014, T027, T045
----------------------------------------------------------------------

【背景】
Legacy Graph Retriever 主要是：直接实体固定高权重、一跳邻居统一固定 hop 权重（例如 +0.35）、实体权重传给 entity_to_records 后累加。这能做补召回，但不同关系/方向被退化成“有边”。

【目标】
Graph Retrieval 根据“用户问什么关系 + 图里是什么关系 + 边是否有原文证据 + 方向/时间/路径是否匹配”来排序 records。

【流程】
Query -> Entity Resolution -> Graph Query Intent -> Seed Nodes
-> Predicate/Direction-aware Traversal -> Evidence-grounded Path Scoring
-> Path -> Record Aggregation -> Graph TopK + Explanation

【Query Entity Resolution 前置规则】
Graph route 优先使用 ER-100/101 输出的 stable entity_id candidates；ambiguous exact alias 不强制唯一；unknown/ambiguous 可有限扩展、降低 Graph 权重或跳过 Graph，Vector/BM25 继续。旧 full-graph substring scan 仅 migration fallback。

【Graph Query Intent】
seed_entities
desired_relation_groups
direction
target_entity_types
max_hops
temporal_constraint

例：“固态电池用什么材料？”
USES_MATERIAL 路径应高于 COMPETES_WITH 路径。

【Path Eligibility】
检查：
seed entity match
grounding_status
predicate compatibility
direction compatibility
target type
temporal compatibility

RELATED_CO_OCCURRENCE 仅作弱补召回。

【Path Score Features】
seed_entity_match
query_entity_importance
relation_match
direction_match
edge_grounding_quality
edge_extraction_confidence
target_type_match
temporal_fit
path_specificity
hop_decay
hub_penalty
provenance/evidence_quality

第一版可线性/乘法组合，但权重必须配置化、可 trace、用 benchmark 调优。
禁止把 +0.8/+0.3/+0.1 等拍脑袋数字当长期真理。

【0-hop / 1-hop / Multi-hop】
Direct entity 与 semantic path 分项计分。
1-hop 是否高分取决于 predicate/direction/grounding/specificity，不由“一跳”本身决定。
默认优先 0~1 hop；只有 MULTI_HOP/关系链问题才 bounded 开 2-hop。

【Hub】
legacy degree threshold 可保留 safety cap，但最终使用 hub_penalty/specificity，防止“技术/中国/人工智能”等超级节点淹没具体关系。

【Path -> Record Aggregation】
通过 edge evidence refs 反查 record_id/evidence_span。
多个独立高价值路径可增分，但重复路径使用 diminishing returns，同 provenance 重复不无限累加。

【Graph Result】
record_id
graph_score
direct_entity_score
semantic_path_score
matched_entities
matched_paths[nodes,predicates,direction_match,relation_match,evidence_refs,path_score,score_breakdown]
rank

【与 RRF】
Graph TopK 通过 T015 RRF/Union 融合。不要把 vector_score+bm25_score+graph_score 直接相加。
Graph score/path features 可给 Reranker/Selector/Trace。

【Legacy】
QA_RELATION_AWARE_GRAPH_RETRIEVAL_ENABLED=false 时保留 fixed-hop legacy baseline/fallback。

【Definition of Done】
- [ ] Graph query 有结构化 GraphQueryIntent。
- [ ] predicate 匹配会改变排序。
- [ ] direction 参与 ranking。
- [ ] ungrounded semantic edge 不参与 high-confidence path。
- [ ] RELATED_CO_OCCURRENCE 只作弱关系。
- [ ] 所有 1-hop 不再统一固定 +0.35。
- [ ] score 有 feature-level breakdown。
- [ ] Direct entity 与 semantic path 分项。
- [ ] hub 有 penalty/cap。
- [ ] 2-hop 仅明确需要时 bounded 开启。
- [ ] record aggregation 防重复 path 无限叠分。
- [ ] Graph TopK 可解释“为什么排第 N”。
- [ ] legacy vs relation-aware 有 benchmark。
- [ ] Graph TopK 仍通过 RRF/Union 与 Vector/BM25 融合。

----------------------------------------------------------------------
【做什么】
保留 original_query；rewrite 输出 rewritten_query + semantic_diff（实体、时间、否定、比较对象、范围变化）；Router/Planner/Entity Resolver 同时看 original+rewrite。Follow-up 只能把上一轮 VERIFIED/SUPPORTED claim+evidence 当 factual premise；raw assistant prose 不作为事实来源。Novelty 采用软惩罚而非盲目 hard-exclude 权威基线来源。
【怎么算完成】
- [ ] rewrite 改错实体/时间/否定会被 diff 检出并回退/升级。
- [ ] previous unverified answer 不会进入下一轮 factual premise。
- [ ] novelty 问题仍可保留必要权威来源，同时寻找新来源。
- [ ] Trace 保存 original/rewrite/diff/context provenance。

T018 - Adaptive Router：FAST / RESEARCH / DEEP 三档模式
优先级：P0
依赖：T014
----------------------------------------------------------------------

【背景】
对所有问题都跑 Planner + Decomposition + 多轮检索，会增加延迟并可能把简单精确事实题“想复杂了”。Agentic 不代表所有请求都多轮。

【目标】
根据问题复杂度和证据需求选择处理深度。Router 必须同时接收 original_query 与 rewritten_query/T042 semantic_diff，不能只相信 rewrite。

【修改范围】
新增：
qa-backend/router.py

【输出 Schema】
question_type
complexity
mode
needs_decomposition
needs_temporal_reasoning
needs_graph
needs_graph_reasoning
graph_intent
needs_multi_source_evidence
needs_multi_document_reasoning
needs_conflict_check
reason

【模式】
FAST_RAG：
Rewrite -> Hybrid Retrieval -> Rerank -> Basic Evidence Check -> Generate -> Verify

RESEARCH_RAG：
Planner/Decompose -> Retrieval -> Ledger -> Grader -> Gap Search (bounded)

DEEP_RESEARCH：
复杂多实体 / 趋势 / 冲突 / 高覆盖要求 -> 完整 iterative loop
当 needs_multi_document_reasoning=true 时，在 Evidence Selector 后启用 Multi-Document Evidence Processing。

【Question Type 至少】
FACT_LOOKUP
ENTITY_OVERVIEW
COMPARISON
MULTI_ENTITY
TREND
TEMPORAL
CAUSAL_ANALYSIS
MULTI_HOP
FOLLOWUP
NOVELTY

【Graph Retrieval Intent 建议】
当 needs_graph=true 或 needs_graph_reasoning=true 时，Router 可输出高层 graph_intent：
- seed_entities
- desired_relation_types / relation_groups
- direction：outgoing / incoming / either
- target_entity_types
- max_hops
- relation_question：true/false

例子：
“固态电池用什么材料？”
应表达为类似：
seed_entity=固态电池
desired_relation_group=USES_MATERIAL / COMPONENT_MATERIAL
direction=outgoing
target_entity_type=material

Router 不需要决定最终 Graph Score；真正的关系匹配与路径评分由 T039 完成。

【Multi-Document Trigger 建议】
以下情况优先 needs_multi_document_reasoning=true：
- 跨公司/跨产品/跨技术路线比较
- 同一问题的证据分散在多篇长文档
- 技术演进/时间序列分析
- 厂商自述 vs 第三方验证
- 多来源相互印证
- 冲突核验
- 需要整合多篇报告后才能覆盖全部 requirements

简单事实查询、单文档摘要、单一精确参数通常不启用。

【实现要求】
1. Router 可用 GLM，但必须严格 JSON + parser tolerance。
2. 明确规则 fallback，例如明显单实体精确参数查询可 FAST。
3. Router failure 不能使整个请求失败。
4. Router 不以省 token 为目标；它的目标是选正确策略和避免语义漂移。
5. 如果 FAST 后 Basic Evidence Check 明显不足，可自动升级到 RESEARCH。
6. 对明显的关系型问题（谁研发、使用什么材料、谁与谁合作、什么替代什么、A 与 B 通过什么关系连接等）应优先设置 needs_graph_reasoning=true；Graph route 不应仅作为普通实体共现补召回。

【Definition of Done】
- [ ] 简单事实题通常走 FAST。
- [ ] comparison/trend/multi-hop 进入 Research 或 Deep。
- [ ] FAST 证据不足可升级模式。
- [ ] Router result 进入 trace。
- [ ] 有 Router accuracy / unnecessary-decomposition benchmark。

T021 - Evidence Ledger：Agent 的核心控制状态
优先级：P0
依赖：T020
----------------------------------------------------------------------

【背景】
Ledger 不能只是日志装饰。如果它不真正控制“是否继续搜、是否允许回答”，那就没有价值。

【目标】
把用户问题拆成可追踪 requirements，并持续维护每个 requirement 的支持、冲突、缺失和独立来源状态。

【修改范围】
新增：
qa-backend/evidence_ledger.py

【Schema】
{
  "question": "...",
  "iteration": 2,
  "requirements": [
    {
      "id": "r1",
      "description": "...",
      "importance": "critical",
      "status": "SUPPORTED",
      "supporting_evidence": [],
      "conflicting_evidence": [],
      "independent_groups": [],
      "temporal_coverage": {},
      "missing": []
    }
  ]
}

Requirement status：
SUPPORTED
PARTIAL
MISSING
CONFLICTED

【实现要求】
1. 每轮 Retrieval + Selector 后 update ledger。
2. supporting_evidence 必须指向 record/evidence objects，不仅是自然语言。
3. independent_groups 使用 provenance 信息。
4. critical requirement 未支持时，不允许仅凭其他部分资料多就整体 SUPPORTED。

【Definition of Done】
- [ ] Ledger 真正参与是否继续搜索。
- [ ] Ledger 真正参与是否允许生成完整答案。
- [ ] critical MISSING 不会被“总文档数量多”掩盖。
- [ ] 支持每轮快照与差异。
- [ ] 有 unit tests 对 coverage/status transition。

T022 - Evidence Grader：Rule Engine + GLM
优先级：P0
依赖：T021, T017
----------------------------------------------------------------------

【背景】
纯 LLM 判断“证据够了吗？”容易自我确认。可确定的 coverage / independence / temporal / conflict 规则应由程序检查。

【目标】
建立可解释的 Evidence Sufficiency 判定。

【修改范围】
新增：
qa-backend/evidence_grader.py

【第一层：Rule Engine】
至少检查：
- critical requirement 是否全部覆盖
- required entity 是否覆盖
- independent provenance groups 数量
- 是否只有 self-reported evidence
- temporal mismatch
- superseded-only evidence
- high severity unresolved contradiction
- required numeric metric 是否缺 unit/condition
- evidence data-quality 是否过低
- citation-capable original text 是否存在
- Graph relation/path 若参与支持，semantic edge 是否全部 evidence-grounded
- Graph path 的 predicate / direction 是否匹配当前 relation requirement

【第二层：GLM Semantic Grader】
判断：
- 证据是否真正回答 requirement
- 是否遗漏重要维度
- 证据逻辑是否足以支持目标结论
- 缺失什么语义证据

【输出】
{
  "overall": "INSUFFICIENT",
  "coverage_score": ...,
  "independent_source_score": ...,
  "rule_failures": [],
  "requirements": [...],
  "missing": [...],
  "next_search_targets": []
}

【硬约束】
- 用户要求比较 A/B/C，B 无 evidence -> 不能 SUPPORTED。
- 用户问“实际是否如此”，只有厂商自述 -> 不应自动 SUPPORTED。
- high-severity unresolved conflict -> 不应直接确定性 SUPPORTED。
- hard rule failure 不能被 GLM一句“足够”覆盖。

【Definition of Done】
- [ ] Grader 不再是单 LLM yes/no。
- [ ] Rule 与 GLM 结果均写 trace。
- [ ] 输出明确 missing/gaps。
- [ ] hard rule failure 有优先级。
- [ ] duplicate/self-report/temporal/conflict 均有测试。

T024 - Iterative Retrieval Orchestrator
优先级：P0
依赖：T023
----------------------------------------------------------------------

【目标】
实现 bounded iterative research loop。

【修改范围】
新增：
qa-backend/orchestrator.py

【核心流程】
1. Rewrite
2. Router
3. 如果需要：Decompose + Plan
4. 执行当前 subqueries

6. RRF/Union Candidate Pool
7. Rerank

stop_reason

【Definition of Done】
- [ ] 复杂问题能执行 >1 轮 targeted retrieval。
- [ ] evidence 足够时提前停止。
- [ ] evidence 无新增时不会死循环。
- [ ] 每轮 state/queries/results 可 trace。
- [ ] FAST 与 Research 流程都能正常工作。

T026 - Knowledge Boundary + Calibrated Abstention
优先级：P0
依赖：T022, T025, T006
----------------------------------------------------------------------

【背景】
“搜索有结果”不代表数据库覆盖足够。特别是开放性、趋势、未来问题，几篇相关资料不能支持宏观结论。

【目标】
判断 Tech-DB 对当前问题的可回答边界，并产生正确的 SUPPORTED / PARTIAL / UNSUPPORTED。

【修改范围】
新增：
qa-backend/knowledge_boundary.py

【Coverage 状态】
HIGH
MEDIUM
LOW
UNKNOWN

【依据】
- requirements coverage
- critical gaps
- evidence count
- independent source groups
- source suitability
- data quality
- temporal coverage
- conflicts
- corpus scope indicators

【关键语义】
“Tech-DB 中未找到”只能推出：
“当前 Tech-DB 没有足够证据”
不能推出：

“没有找到 X” != “X 不存在”。

【用户输出】

UNSUPPORTED：
“已检索 X/Y/Z 方向，但当前数据库仍缺少关键证据，因此无法可靠回答。”

可选显示：
- 缺的具体证据
- 已覆盖范围
- KB snapshot/update date

【Definition of Done】
- [ ] related docs 很多但 critical coverage 不足时可 PARTIAL。
- [ ] 无核心 evidence 时 UNSUPPORTED。
- [ ] “not found” 不转成现实世界负事实。
- [ ] coverage/boundary 进入 benchmark。
- [ ] abstention precision/recall 可统计。

evidence_span
ambiguous
extraction_confidence

【实现要求】
1. 数字必须能回到 exact evidence span。
2. 单位转换由确定性代码完成。
3. 百分比、倍数、差值等基础数学由程序计算。
4. 条件不一致时禁止无提示直接比较。
5. 如“最高”“典型”“实验室”“单 GPU”“系统总量”等 qualifier 必须保留。
6. 单位/条件无法确定 -> ambiguous=true，不猜。
7. Numeric Claim verification 对比：
   value
   unit
   condition
   time
8. 不把 key_params 中模型生成的结构字段当作比原文更高权威；它是索引，原文才是证据。

【Definition of Done】
- [ ] 常见技术单位可标准化/转换。
- [ ] Gb/s vs GB/s 等维度错误可检测。
- [ ] per-device vs system-total 不会直接比较。
- [ ] numeric claim 可 deterministic verify。
- [ ] 有不同单位/条件的 comparison 测试。

T030 - Active Conflict Detection
优先级：P0/P1
依赖：T021, T010, T029
----------------------------------------------------------------------

【背景】
现有 epistemic verifier 可以在答案后检查 CONFLICT_IGNORED，但高质量系统应该在生成前就知道证据冲突。

【目标】
识别支持、真实冲突、不同 scope、版本更新，并在必要时触发 targeted retrieval。

【修改范围】
新增：
qa-backend/conflict_detector.py

【比较维度】
subject
predicate/metric
graph_relation_direction
time
scope/condition
value
source role

【分类】
AGREE
CONTRADICT
DIFFERENT_SCOPE
VERSION_UPDATE
UNKNOWN

【例子】
2024 路线图 vs 2026 正式发布：
VERSION_UPDATE

单 GPU 1.8TB/s vs 8-GPU system aggregate：
DIFFERENT_SCOPE

两个同时间同条件来源给出不同值：
CONTRADICT candidate

【实现要求】
1. 生成前扫描 Ledger 中可能指向同一 atomic fact 的 evidence。
2. deterministic 数值/时间比较优先。
3. GLM 只处理 scope/semantic ambiguity。
4. high severity contradiction -> Gap Analysis 生成 resolution query。
5. targeted search 后仍冲突 -> Ledger 保持 CONFLICTED。
6. Generator 必须显式呈现 unresolved conflict，不得选一个值装成唯一事实。
7. self-report vs independent measurement 的差异不能简单视为同等事实冲突，需要 evidence_role。
8. Graph semantic relation 按 subject/predicate/object/direction/time 对齐后再判断冲突。

【Definition of Done】
- [ ] 可区分 VERSION_UPDATE 和 CONTRADICT。
- [ ] 可区分 DIFFERENT_SCOPE。
- [ ] unresolved conflict 会影响 overall status / wording。
- [ ] conflict triggers 可产生 targeted retrieval。
- [ ] 有 conflict benchmark。

T038 - Multi-Document Evidence Processing / Document Evidence Workers
优先级：P0/P1
依赖：T017, T021, T028, T030；并复用 T003 exact grounding
----------------------------------------------------------------------

【背景】
复杂技术问题的答案经常分散在多篇文档里。即使 Reranker 已经选出最相关的文档，仍然存在：
- 多篇文档分别覆盖不同 requirement；
- 同一实体的不同规格/代际资料容易串线；
- 标题高度相关，但正文实际没有可用证据；
- 多篇文档之间可能互相印证、补充或冲突；
- 直接把多篇整文塞进 Generator 会增加上下文混淆。

Multi-Document Agent 的正确落地方式不是“给数据库每篇文档常驻一个 Agent”，也不是再建设一套与现有 Agentic RAG 平行的系统。

本 Ticket 把它实现为现有 RESEARCH_RAG / DEEP_RESEARCH 内部的一个按需能力：
Evidence Selector 先选出值得深读的少量关键文档，再由临时 Document Evidence Workers 并行对每篇文档做结构化证据提取，最后统一合并进 Evidence Ledger。

【目标】
建立：
Selected Documents
-> Parallel Document Evidence Workers
-> Structured Evidence Packets
-> Exact Span Validation
-> Cross-Document Merge / Dedup / Conflict Detection
-> Evidence Ledger

Document Worker 的职责是：
extract / locate / structure / classify

Document Worker 的职责不是：
直接回答用户问题 / 决定总体 SUPPORTED / 使用模型预训练知识补证据。

【触发条件】
由 T018 Router 输出：
needs_multi_document_reasoning=true

典型触发：
- 跨公司 / 跨产品比较
- 技术路线演进
- 厂商自述 vs 第三方验证
- 多来源相互印证
- 多篇报告共同覆盖一个复杂 requirement
- 来源冲突核验
- 长文档中的证据分散在不同位置

通常不触发：
- 单一事实查询
- 单篇文档摘要
- 一个 record 已能充分支持的精确参数问题

【修改范围】
新增建议：
qa-backend/multi_document.py
或：
qa-backend/document_worker.py
qa-backend/multi_document_processor.py

可新增 schema：
DocumentEvidencePacket
CrossDocumentEvidenceSet

【Document Worker 输入】
- original question
- 当前 requirement / gap
- canonical entities
- temporal constraints
- source/provenance metadata
- 一篇 selected document
- 可选 chunk hits / parent context

不要给 Document Worker：
- 其他文档的结论
- Generator draft
- 最终回答
避免它被其他来源污染后“替某篇文档说话”。

【Document Worker 输出 Schema 建议】
{
  "record_id": 123,
  "requirement_id": "r2",
  "relevant": true,
  "evidence_found": true,
  "claims": [
    {
      "local_claim": "...",
      "epistemic_type": "VERIFIABLE_FACT",
      "evidence_span": "...",
      "start": 1200,
      "end": 1340,
      "grounding_status": "VALID"
    }
  ],
  "numeric_facts": [],
  "entities": [],
  "temporal_scope": {},
  "source_role": "self_reported",
  "internal_conflicts": [],
  "unanswered_aspects": []
}

【核心规则】
1. Worker 必须按单篇文档隔离执行。
2. 每个 local claim 必须绑定该文档的 exact evidence span。
3. evidence_span 必须通过 T003 的程序级原文 substring/offset 验证。
4. Worker 不允许输出“根据常识/模型知识”的事实。
5. Worker 可以返回：
   relevant=true, evidence_found=false
   用来识别“标题/主题相关，但正文没有真正证据”的候选。
6. Worker 不决定 overall answer status。
7. Worker 不决定跨文档冲突最终如何解释。
8. Worker 不把 synthetic summary 当 original evidence。
9. Worker 输出必须结构化，可直接被 Ledger/Conflict Detector 消费。
10. Document Workers 可并行，但必须 per-request 隔离状态。

【Cross-Document Merge】
对所有 DocumentEvidencePacket 统一处理：
- 按 requirement 合并
- 按 provenance_root/independent_group 去重
- entity canonicalization
- temporal alignment
- numeric condition alignment
- conflict detection
- evidence coverage update

禁止简单：
“把 N 个 Worker 的自然语言总结再让另一个 LLM 总结一次”
作为唯一合并逻辑。

能够由程序完成的 merge / dedup / group / numeric / temporal 对齐优先用确定性逻辑。

【与其他模块职责边界】

T017 Evidence Selector：
回答“哪些文档值得深读？”

T038 Multi-Document Evidence Processing：
回答“这些文档内部到底分别有哪些可验证证据？”

T021 Evidence Ledger：
回答“每个 requirement 当前有什么证据、还缺什么？”

T030 Conflict Detector：
回答“不同文档证据之间是 agree / conflict / different scope / version update？”

T022 Evidence Grader：
回答“整个证据集合是否已经足以回答用户问题？”

T031 Context Builder：
把经过处理的跨文档证据组织成最终 Generator Evidence Package。

【性能与规模】
不要为全库每篇文档创建常驻 Agent。

建议：
- Reranker / Evidence Selector 先缩到少量关键文档，例如 5~15 篇；
- 只有这些文档进入 Document Workers；
- worker 并发数配置化；
- 同一 record/requirement 已处理过且文档版本未变化时，可在当前请求内复用 packet。

这里的限制主要为了稳定性、避免上下文爆炸和重复推理，而不是为了省 API 成本。

【Trace】
必须记录：
- 为什么启用 multi-document mode
- selected document IDs
- 每个 worker 的 requirement
- worker evidence_found true/false
- exact spans
- provenance group
- merge/dedup 结果
- cross-document conflict
- 最终对 Ledger 的增量

【Definition of Done】
- [ ] Router 能通过 needs_multi_document_reasoning 按需启用该模式。
- [ ] 系统不会给 Tech-DB 全库创建常驻 document agents。
- [ ] Selected Documents 可并行进入 Document Evidence Workers。
- [ ] 每个 Worker 只基于自己的 document + requirement 提取证据。
- [ ] Worker 输出结构化 DocumentEvidencePacket，而不是最终答案。
- [ ] 每个有效 local claim 都有 exact evidence span。
- [ ] evidence span 无法在原文验证时，该 local claim 不得进入 Ledger。
- [ ] 能识别 relevant=true 但 evidence_found=false 的候选。
- [ ] 多文档 packet 能按 provenance 去重。
- [ ] 能把跨文档冲突交给 T030 处理。
- [ ] merge 结果能更新 T021 Evidence Ledger。
- [ ] T031 能消费 multi-document evidence packets 生成 Evidence Package。
- [ ] 整个模式可 trace、可 feature flag、可关闭回退到原有 Research RAG。

【测试】
至少新增以下端到端 cases：

Case A：跨公司比较
问题要求 A/B/C 三家公司多个技术维度。
验证：
- 多文档模式触发；
- 每家公司关键文档分别处理；
- 不因 A 文档多而挤掉 B/C；
- Ledger 覆盖对象 x 维度。

Case B：标题相关但无正文证据
某篇文档标题高度相关，但正文没有目标数字。
验证：
relevant=true, evidence_found=false；
不得生成 citation。

Case C：厂商自述 vs 第三方验证
验证两类 source_role 被保留；
不能把厂商 claim 自动升级为独立事实。

Case D：版本冲突
旧 roadmap 与新正式发布资料。
验证 Cross-Document Merge 后交给 Conflict Detector，并得到 VERSION_UPDATE，而不是错误 CONTRADICT。

Case E：真实冲突
同时间同条件两个独立来源给出不同数值。
验证：
CONFLICTED；
若补搜后仍无法解决，最终答案显式说明冲突。

Case F：单一事实查询
验证：
needs_multi_document_reasoning=false；
不启动 Document Workers。

【Benchmark 指标】
新增：
- multi_document_trigger_accuracy
- document_worker_evidence_precision
- document_worker_span_validity
- cross_document_requirement_coverage
- cross_document_redundancy
- provenance_dedup_accuracy
- cross_document_conflict_accuracy
- multi_document_answer_gain vs standard Research RAG

T031 - Evidence-aware Context Assembly / Packing
优先级：P0
依赖：T017, T021, T030；Multi-Document Mode 下额外消费 T038 输出
----------------------------------------------------------------------

【背景】
把 Reranker Top10/Top25 按分数直接拼 prompt，会造成重复、对象失衡、冲突证据消失、上下文 token 被无价值内容占用。

把最终输入 Generator 的内容组织成“Evidence Package”，而不是“Search Results Dump”。

【修改范围】
新增：
qa-backend/context_builder.py

【组织格式】
Question
Research assumptions/scope
Requirement R1
  Supporting Evidence
  Conflicting Evidence
  Provenance/Source Role
  Temporal metadata
  Exact/Relevant Spans
Requirement R2
...

【实现要求】
1. 按 requirement 分组。
2. 当 T038 Multi-Document Evidence Processing 已运行时，优先消费其经过 exact-span 验证的 Structured Evidence Packets，而不是重新把整篇文档塞进 Generator。
3. 对同源重复证据压缩，只保留必要代表。
4. conflict 必须保留，不能因为排名低而消失。

11. 如果某 requirement MISSING，明确告诉 Generator “缺失”，不要让 Generator 用预训练知识补。

【Definition of Done】
- [ ] Generator context 能看出每个 requirement 的 support/gap/conflict。
- [ ] 高度重复证据显著减少。
- [ ] comparison 对象不会因 source 数量差异严重失衡。
- [ ] conflict evidence 不被丢弃。
- [ ] Evidence Package 可序列化/trace。

T032 - Claim-aware Citation Snippet + Multi-span + Highlight
优先级：P0
依赖：T003, T004
----------------------------------------------------------------------

【背景】
用户要求参考来源下面显示与回答真正相关的那段正文，而不是正文从第一个字开始。更进一步，snippet 应说明“这条来源具体支持回答里的哪条结论”。

【目标】
把 citation UI 数据升级成真正的 Evidence Card 数据。

【Citation Schema】
{
  "id": 3,
  "record_id": 123,
  "title": "...",
  "source": "...",
  "date": "...",
  "url": "...",
  "source_type": "company_technical_doc",
  "source_label": "官方一手资料",
  "supports_claim_ids": ["claim_001"],
  "supports_claim_texts": ["单 GPU 双向带宽达到 ..."],

      "end": 1371,
      "highlight": "1.8 TB/s 的双向带宽",

    }
  ]
}

同一来源若支持两个相隔很远的 claim：

- citation invalid
- 重新找来源/重写 claim/再检索

【Definition of Done】
- [ ] 每个有效 reference 的 snippet 是 claim-aware，不是 query-only。
- [ ] 支持 multi-span。
- [ ] 支持 exact offsets。
- [ ] highlight 对应 claim。
- [ ] invalid span 永不展示成有效证据。
- [ ] query-based excerpt 只可保留作为内部 retrieval/debug，不作为最终证据卡核心。

UNVERIFIED

timeout/API error：retry。

trace 保存 failure reason。

【Definition of Done】

- [ ] malformed JSON 永不静默 PASS。
- [ ] retry 存在。
- [ ] UNVERIFIED 可进入最终 API。
- [ ] 单测覆盖 exception / malformed / empty / timeout。

T008 - Probabilistic Provenance Clustering / 同源证据识别
优先级：P0
依赖：T007
----------------------------------------------------------------------

【背景】
多家媒体转载同一个原始新闻时，文档数量不代表证据独立性。现实转载可能改标题、改顺序、加入少量评论，因此不能只用 exact duplicate，也不能声称 100% 确定来源血缘。

【目标】
建立概率式 provenance clustering，识别“可能同源”的内容，让在线系统统计 independent evidence groups，而不是 document count。

【输入特征】
- canonical URL
- original URL
- redirect/source link
- domain
- explicit citation links
- title normalized similarity
- body text similarity
- embedding similarity
- publish/event time difference
- entity overlap
- existing event cluster
- source attribution phrase

【输出】
same_origin_probability
provenance_root_id
independent_group_id
provenance_confidence
provenance_reason/features

【实现要求】
1. 使用确定性特征 + 相似度模型组合。
2. 阈值配置化：
   - high confidence -> 合并 provenance group
   - ambiguous band -> uncertain，不强制合并
   - low -> independent candidate
3. existing dedup / cluster 作为 feature，不直接等同 provenance。
4. 后续 Evidence Grader 的独立证据数以 independent_group_id 为主。
5. 一个二手文章即使基于原始报道，也可能包含独立采访/新增数据；后续允许 claim-level provenance 扩展，第一版至少不要整篇一刀切成绝对同源。
6. trace 输出某候选被判重复来源的原因。

【Definition of Done】
- [ ] 明显全文转载能聚为同组。
- [ ] 改标题但正文高度相似的转载能聚为同组。
- [ ] 独立报道同一事件不会仅因为主题相同全部合并。
- [ ] ambiguous case 保留 probability。
- [ ] Evidence Selector/Grader 可读取 independent_group_id。
- [ ] 5 篇同源转载不会在独立证据计数中记为 5。

【测试】
建立小样本：
A. 5 篇同源转载
B. 3 篇独立采访同一事件
C. 1 篇转载但新增独立测试数据
检查 group 与 uncertain 情况。

【新流程】

BM25 TopK
Graph TopK
-> RRF / Union / Dedup
-> High-recall Candidate Pool
-> Reranker
-> Evidence Selector

6. benchmark 三种方案：
   A. old RRF Top25

【Definition of Done】

- [ ] 单路强相关 outlier 不会因过早 Top25 被轻易丢失。

T016 - Content-aware Reranker
优先级：P0

----------------------------------------------------------------------

【背景】

【目标】

【修改范围】

qa-backend/reranker.py

async def rerank(query, candidates, top_k=None, context=None) -> list

输出至少：
record_id
rerank_score
input_rank
reason(optional)

【实现策略】

- Fast cross-encoder 先排 100~150
- 高质量复杂题可让 GLM 再判断 Top20~40

【输入内容】

- title

- relevant body/chunk text

【Definition of Done】
- [ ] 存在真实的 query-document 内容级 rerank stage。
- [ ] 支持 batch/listwise。
- [ ] Rerank 结果进入 trace。
- [ ] 对旧 RRF Top25 有 relevance benchmark。
- [ ] Reranker error 有 fallback，不会把所有候选清空。
- [ ] 不把 generated synthetic summary 当唯一 rerank evidence。

T017 - Evidence Selector：从“相关文档”选出“最佳证据组合”
优先级：P0

----------------------------------------------------------------------

【背景】
即使 Reranker 很准，Top10 也可能全是同一个厂商、同一转载链、同一事件角度。最终上下文要优化的是 Evidence Set，而非单文档排序。

【目标】
构建 source-aware / provenance-aware / temporal-aware / coverage-aware 的 Evidence Selector。

【输入】
Reranked candidates
Evidence metadata
Current requirement / Evidence Ledger
Temporal intent

【选择特征】
- rerank relevance
- requirement coverage gain
- source suitability
- independent_group gain
- temporal fit
- entity balance
- event diversity
- data quality
- redundancy penalty
- novelty gain

可建立配置化 selection_score，但不要把公式视为真理。

【重要规则】
1. 同一 provenance group 默认限制重复占位。
2. 比较 A/B/C 时，若 B 的高质量证据存在，不允许 A 因资料多把所有名额占满。
3. Diversity 是软约束，不能为了“多样”选明显不相关来源。
4. 对于需要官方规格的问题，一条高适配官方一手资料可以比多家二手转载重要。
5. 每条选择/淘汰给出 machine-readable reason。

【Definition of Done】
- [ ] 最终 Evidence Set 不被同源转载占满。
- [ ] comparison case 主要对象都有合理 coverage。
- [ ] Selector 能读取 provenance/temporal/data-quality/suitability。
- [ ] 输出 selected/rejected reasons 到 trace。
- [ ] A/B benchmark 比较 reranker-only vs selector。

T018 - Adaptive Router：FAST / RESEARCH / DEEP 三档模式
优先级：P0
依赖：T014
----------------------------------------------------------------------

【背景】
对所有问题都跑 Planner + Decomposition + 多轮检索，会增加延迟并可能把简单精确事实题“想复杂了”。Agentic 不代表所有请求都多轮。

【目标】
根据问题复杂度和证据需求选择处理深度。

【修改范围】
新增：
qa-backend/router.py

【输出 Schema】
question_type
complexity
mode
needs_decomposition
needs_temporal_reasoning
needs_graph
needs_multi_source_evidence
needs_conflict_check
reason

【模式】
FAST_RAG：
Rewrite -> Hybrid Retrieval -> Rerank -> Basic Evidence Check -> Generate -> Verify

RESEARCH_RAG：
Planner/Decompose -> Retrieval -> Ledger -> Grader -> Gap Search (bounded)

DEEP_RESEARCH：
复杂多实体 / 趋势 / 冲突 / 高覆盖要求 -> 完整 iterative loop

【Question Type 至少】
FACT_LOOKUP
ENTITY_OVERVIEW
COMPARISON
MULTI_ENTITY
TREND
TEMPORAL
CAUSAL_ANALYSIS
MULTI_HOP
FOLLOWUP
NOVELTY

【实现要求】
1. Router 可用 GLM，但必须严格 JSON + parser tolerance。
2. 明确规则 fallback，例如明显单实体精确参数查询可 FAST。
3. Router failure 不能使整个请求失败。
4. Router 不以省 token 为目标；它的目标是选正确策略和避免语义漂移。
5. 如果 FAST 后 Basic Evidence Check 明显不足，可自动升级到 RESEARCH。

【Definition of Done】
- [ ] 简单事实题通常走 FAST。
- [ ] comparison/trend/multi-hop 进入 Research 或 Deep。
- [ ] FAST 证据不足可升级模式。
- [ ] Router result 进入 trace。
- [ ] 有 Router accuracy / unnecessary-decomposition benchmark。

T019 - Query Decomposition
优先级：P0
依赖：T018

【背景】
复杂问题一次搜索常只覆盖一部分。例如比较多个公司多个维度，需要明确知道“哪些维度必须有证据”。

【目标】

【输出】
{

      "id": "r1",

      "entities": ["org:nvidia"],
      "dimensions": ["interconnect"],
      "queries": [...]
    }
  ]
}

【实现要求】
1. requirements 必须能映射回原始用户意图。

T021 - Evidence Ledger：Agent 的核心控制状态
优先级：P0
依赖：T020
----------------------------------------------------------------------

【背景】
Ledger 不能只是日志装饰。如果它不真正控制“是否继续搜、是否允许回答”，那就没有价值。

【目标】
把用户问题拆成可追踪 requirements，并持续维护每个 requirement 的支持、冲突、缺失和独立来源状态。

【修改范围】
新增：
qa-backend/evidence_ledger.py

【Schema】
{
  "question": "...",
  "iteration": 2,
  "requirements": [
    {
      "id": "r1",
      "description": "...",
      "importance": "critical",
      "status": "SUPPORTED",
      "supporting_evidence": [],
      "conflicting_evidence": [],
      "independent_groups": [],
      "temporal_coverage": {},
      "missing": []
    }
  ]
}

Requirement status：
SUPPORTED
PARTIAL
MISSING
CONFLICTED

【实现要求】
1. 每轮 Retrieval + Selector 后 update ledger。
2. supporting_evidence 必须指向 record/evidence objects，不仅是自然语言。
3. independent_groups 使用 provenance 信息。
4. critical requirement 未支持时，不允许仅凭其他部分资料多就整体 SUPPORTED。
5. stopping criteria 读取 Ledger。
6. context builder 读取 Ledger。
7. Generator 输入包含 Ledger-derived evidence package。
8. Trace 保存每轮 immutable snapshot，方便回放。
9. 新证据不能直接覆盖旧冲突证据，保留历史决策。

【Definition of Done】
- [ ] Ledger 真正参与是否继续搜索。
- [ ] Ledger 真正参与是否允许生成完整答案。
- [ ] critical MISSING 不会被“总文档数量多”掩盖。
- [ ] 支持每轮快照与差异。
- [ ] 有 unit tests 对 coverage/status transition。

T022 - Evidence Grader：Rule Engine + GLM
优先级：P0
依赖：T021, T017
----------------------------------------------------------------------

【背景】
纯 LLM 判断“证据够了吗？”容易自我确认。可确定的 coverage / independence / temporal / conflict 规则应由程序检查。

【目标】
建立可解释的 Evidence Sufficiency 判定。

【修改范围】
新增：
qa-backend/evidence_grader.py

【第一层：Rule Engine】
至少检查：
- critical requirement 是否全部覆盖
- required entity 是否覆盖
- independent provenance groups 数量
- 是否只有 self-reported evidence
- temporal mismatch
- superseded-only evidence
- high severity unresolved contradiction
- required numeric metric 是否缺 unit/condition
- evidence data-quality 是否过低
- citation-capable original text 是否存在

【第二层：GLM Semantic Grader】
判断：
- 证据是否真正回答 requirement
- 是否遗漏重要维度
- 证据逻辑是否足以支持目标结论
- 缺失什么语义证据

【输出】
{
  "overall": "INSUFFICIENT",
  "coverage_score": ...,
  "independent_source_score": ...,
  "rule_failures": [],
  "requirements": [...],
  "missing": [...],
  "next_search_targets": []
}

【硬约束】
- 用户要求比较 A/B/C，B 无 evidence -> 不能 SUPPORTED。
- 用户问“实际是否如此”，只有厂商自述 -> 不应自动 SUPPORTED。
- high-severity unresolved conflict -> 不应直接确定性 SUPPORTED。
- hard rule failure 不能被 GLM一句“足够”覆盖。

【Definition of Done】
- [ ] Grader 不再是单 LLM yes/no。
- [ ] Rule 与 GLM 结果均写 trace。
- [ ] 输出明确 missing/gaps。
- [ ] hard rule failure 有优先级。
- [ ] duplicate/self-report/temporal/conflict 均有测试。

T023 - Gap Analysis + Targeted Query Generation

【输出】
{
  "gaps": [...],

【Gap 类型至少】

T024 - Iterative Retrieval Orchestrator
优先级：P0
依赖：T023
----------------------------------------------------------------------

【背景】
真正 Agentic 的核心不是“用了 Agent 名字”，而是存在受控的 Retrieve -> Grade -> Gap -> Retrieve Again 闭环。

【目标】
实现 bounded iterative research loop。

【修改范围】
新增：
qa-backend/orchestrator.py

【核心流程】
1. Rewrite
2. Router
3. 如果需要：Decompose + Plan
4. 执行当前 subqueries
5. Vector/BM25/Graph
6. RRF/Union Candidate Pool
7. Rerank
8. Evidence Selector
9. Update Ledger
10. Conflict Detection
11. Evidence Grader
12. sufficient -> 进入 generation
13. insufficient -> Gap Analysis
14. 新 subqueries -> 下一轮
15. Stop Criteria -> Partial/Unsupported

【推荐配置】
MAX_ITERATIONS = 4~6
MAX_SUBQUERIES = 8~12
MAX_TOOL_CALLS = 配置化
MAX_RERANK_CANDIDATES = 150~200

这些 bound 用于稳定性和防漂移，不是成本优先。

【实现要求】
1. FAST_RAG 不强制完整 loop。
2. RESEARCH/DEEP 使用同一 typed ResearchState。
3. 每轮只重点处理 unresolved requirements。
4. Candidate/evidence 跨轮去重。
5. 保留 novelty follow-up 能力，但从“排除过去引用记录”升级为“已覆盖 evidence/requirement aware”，避免为了新颖而排除仍需比较的关键来源。
6. 每轮 state 可序列化进 trace。
7. 异常模块要安全降级，不能无状态继续生成。

【建议 ResearchState】
original_query
rewritten_query
query_type
mode
plan
subqueries
retrieval_rounds
candidate_records
selected_evidence
evidence_ledger
contradictions
unresolved_gaps
status
stop_reason

【Definition of Done】
- [ ] 复杂问题能执行 >1 轮 targeted retrieval。
- [ ] evidence 足够时提前停止。
- [ ] evidence 无新增时不会死循环。
- [ ] 每轮 state/queries/results 可 trace。
- [ ] FAST 与 Research 流程都能正常工作。

T026 - Knowledge Boundary + Calibrated Abstention
优先级：P0
依赖：T022, T025, T006
----------------------------------------------------------------------

【背景】
“搜索有结果”不代表数据库覆盖足够。特别是开放性、趋势、未来问题，几篇相关资料不能支持宏观结论。

【目标】
判断 Tech-DB 对当前问题的可回答边界，并产生正确的 SUPPORTED / PARTIAL / UNSUPPORTED。

【修改范围】
新增：
qa-backend/knowledge_boundary.py

【Coverage 状态】
HIGH
MEDIUM
LOW
UNKNOWN

【依据】
- requirements coverage
- critical gaps
- evidence count
- independent source groups
- source suitability
- data quality
- temporal coverage
- conflicts
- corpus scope indicators

【关键语义】
“Tech-DB 中未找到”只能推出：
“当前 Tech-DB 没有足够证据”
不能推出：
“现实世界不存在 X”。

对 negative claim 尤其如此：
“没有找到 X” != “X 不存在”。

【用户输出】
PARTIALLY_SUPPORTED：
“可以确认：A、B。当前数据库缺少 C，因此无法可靠完成完整比较。”

UNSUPPORTED：
“已检索 X/Y/Z 方向，但当前数据库仍缺少关键证据，因此无法可靠回答。”

可选显示：
- 缺的具体证据
- 已覆盖范围
- KB snapshot/update date

【Definition of Done】
- [ ] related docs 很多但 critical coverage 不足时可 PARTIAL。
- [ ] 无核心 evidence 时 UNSUPPORTED。
- [ ] “not found” 不转成现实世界负事实。
- [ ] coverage/boundary 进入 benchmark。
- [ ] abstention precision/recall 可统计。

T028 - Contextual Chunking + Parent/Child Retrieval
优先级：P1
依赖：T016
----------------------------------------------------------------------

【背景】
长文章、长报告、论文的关键事实可能出现在正文中后部。整篇 record embedding 会稀释局部信号；固定截断又容易丢上下文。

【目标】
建立小粒度精准召回 + Parent Record 上下文恢复。

【修改范围】
新增建议：
scripts/build_chunk_index.py

【Chunk Schema】
chunk_id

start_offset
end_offset
section

title
source
date
category

【切分原则】

- [ ] chunk index 与 data snapshot/version 绑定。

【背景】
Tech-DB 技术回答大量包含带宽、容量、效率、温度、功率、倍率、密度、规模等参数。LLM 容易混淆 Gb/s 与 GB/s、单卡与整机、实验条件与商用条件。

【目标】
把关键参数抽成结构化、可确定性验证的数据，并限制错误比较。

【修改范围】
新增：
scripts/extract_numeric_facts.py
qa-backend/numeric_facts.py

【Schema】
metric
value
unit
normalized_value
normalized_unit
condition
entity_id
event/published date
record_id
evidence_span
ambiguous
extraction_confidence

【实现要求】
1. 数字必须能回到 exact evidence span。
2. 单位转换由确定性代码完成。
3. 百分比、倍数、差值等基础数学由程序计算。
4. 条件不一致时禁止无提示直接比较。
5. 如“最高”“典型”“实验室”“单 GPU”“系统总量”等 qualifier 必须保留。
6. 单位/条件无法确定 -> ambiguous=true，不猜。
7. Numeric Claim verification 对比：
   value
   unit
   condition
   time
8. 不把 key_params 中模型生成的结构字段当作比原文更高权威；它是索引，原文才是证据。

【Definition of Done】
- [ ] 常见技术单位可标准化/转换。
- [ ] Gb/s vs GB/s 等维度错误可检测。
- [ ] per-device vs system-total 不会直接比较。
- [ ] numeric claim 可 deterministic verify。
- [ ] 有不同单位/条件的 comparison 测试。

T030 - Active Conflict Detection
优先级：P0/P1
依赖：T021, T010, T029
----------------------------------------------------------------------

【背景】
现有 epistemic verifier 可以在答案后检查 CONFLICT_IGNORED，但高质量系统应该在生成前就知道证据冲突。

【目标】
识别支持、真实冲突、不同 scope、版本更新，并在必要时触发 targeted retrieval。

【修改范围】
新增：
qa-backend/conflict_detector.py

【比较维度】
subject
predicate/metric
time
scope/condition
value
source role

【分类】
AGREE
CONTRADICT
DIFFERENT_SCOPE
VERSION_UPDATE
UNKNOWN

【例子】
2024 路线图 vs 2026 正式发布：
VERSION_UPDATE

单 GPU 1.8TB/s vs 8-GPU system aggregate：
DIFFERENT_SCOPE

两个同时间同条件来源给出不同值：
CONTRADICT candidate

【实现要求】
1. 生成前扫描 Ledger 中可能指向同一 atomic fact 的 evidence。
2. deterministic 数值/时间比较优先。
3. GLM 只处理 scope/semantic ambiguity。
4. high severity contradiction -> Gap Analysis 生成 resolution query。
5. targeted search 后仍冲突 -> Ledger 保持 CONFLICTED。
6. Generator 必须显式呈现 unresolved conflict，不得选一个值装成唯一事实。
7. self-report vs independent measurement 的差异不能简单视为同等事实冲突，需要 evidence_role。

【Definition of Done】
- [ ] 可区分 VERSION_UPDATE 和 CONTRADICT。
- [ ] 可区分 DIFFERENT_SCOPE。
- [ ] unresolved conflict 会影响 overall status / wording。
- [ ] conflict triggers 可产生 targeted retrieval。
- [ ] 有 conflict benchmark。

T031 - Evidence-aware Context Assembly / Packing
优先级：P0
依赖：T017, T021, T030
----------------------------------------------------------------------

【背景】
把 Reranker Top10/Top25 按分数直接拼 prompt，会造成重复、对象失衡、冲突证据消失、上下文 token 被无价值内容占用。

【目标】
把最终输入 Generator 的内容组织成“Evidence Package”，而不是“Search Results Dump”。

【修改范围】
新增：
qa-backend/context_builder.py

【组织格式】
Question
Research assumptions/scope
Requirement R1
  Supporting Evidence
  Conflicting Evidence
  Provenance/Source Role
  Temporal metadata
  Exact/Relevant Spans
Requirement R2
...

【实现要求】
1. 按 requirement 分组。
2. 对同源重复证据压缩，只保留必要代表。
3. conflict 必须保留，不能因为排名低而消失。
4. source role 清晰，例如 self_reported / independent。
5. 优先给 exact/relevant original span；必要时附 parent context。
6. Token budget 按 evidence value/coverage 分配，不按纯检索排名。
7. synthetic summary 不作为 evidence。
8. untrusted retrieved text 以 data boundary 包装。
9. 如果某 requirement MISSING，明确告诉 Generator “缺失”，不要让 Generator 用预训练知识补。

【Definition of Done】
- [ ] Generator context 能看出每个 requirement 的 support/gap/conflict。
- [ ] 高度重复证据显著减少。
- [ ] comparison 对象不会因 source 数量差异严重失衡。
- [ ] conflict evidence 不被丢弃。
- [ ] Evidence Package 可序列化/trace。

T032 - Claim-aware Citation Snippet + Multi-span + Highlight
优先级：P0
依赖：T003, T004
----------------------------------------------------------------------

【背景】
用户要求参考来源下面显示与回答真正相关的那段正文，而不是正文从第一个字开始。更进一步，snippet 应说明“这条来源具体支持回答里的哪条结论”。

【目标】
把 citation UI 数据升级成真正的 Evidence Card 数据。

【Citation Schema】
{
  "id": 3,
  "record_id": 123,
  "title": "...",
  "source": "...",
  "date": "...",
  "url": "...",
  "source_type": "company_technical_doc",
  "source_label": "官方一手资料",
  "supports_claim_ids": ["claim_001"],
  "supports_claim_texts": ["单 GPU 双向带宽达到 ..."],
  "evidence_spans": [
    {
      "text": "...",
      "start": 1203,
      "end": 1371,
      "highlight": "1.8 TB/s 的双向带宽",
      "grounding_status": "VALID"
    }
  ]
}

【Multi-span】
同一来源若支持两个相隔很远的 claim：
- 最多默认展示 1~2 个最佳 span。
- 中间用“……”。
- 不为了覆盖两个位置拉出 2000 字长块。

【Highlight】
只高亮最直接 support claim 的词组/句子，不整段全高亮。

【Fallback 规则】
如果 exact grounding 失败：
- citation invalid
- 重新找来源/重写 claim/再检索
绝不回退“正文开头”。

【Definition of Done】
- [ ] 每个有效 reference 的 snippet 是 claim-aware，不是 query-only。
- [ ] 支持 multi-span。
- [ ] 支持 exact offsets。
- [ ] highlight 对应 claim。
- [ ] invalid span 永不展示成有效证据。
- [ ] query-based excerpt 只可保留作为内部 retrieval/debug，不作为最终证据卡核心。

T033 - Reference Card Frontend / 答案证据 UI
优先级：P1
依赖：T032, T006, T009
----------------------------------------------------------------------

【背景】
用户看 citation 的目的不是确认“有链接”，而是快速审计“为什么这篇来源支持这个回答”。

【目标】
把答案下方参考来源升级为可审计 Evidence Card。

【推荐 UI】
[3] NVIDIA Blackwell Architecture
NVIDIA · 官方一手资料/厂商自述 · 日期

• Claim B

【来源标签】
可以：

学术论文
第三方报道
厂商自述
二手转载

不要：

6. 前端对旧 API citation schema 做兼容 fallback，便于渐进上线。

【Definition of Done】
- [ ] 用户无需打开原文即可理解“这条来源支持什么”。
- [ ] 可展开上下文。
- [ ] 可跳转原文。
- [ ] source label 不制造虚假精确性。
- [ ] PARTIAL/UNSUPPORTED/UNVERIFIED UI 正确。
- [ ] 桌面与移动端不出现明显布局破坏。

======================================================================
补充横切要求：数据版本、证据可复现、部署安全
======================================================================

这些要求跨多个 Ticket 实现，不单独拆新票，但不能遗漏：

A. Evidence Immutability / Reproducibility
- record 建议保存 content_hash。
- index release 绑定 dataset snapshot/version。
- evidence span 与 content_hash 关联。
- URL 后续内容变化时，系统至少能知道当前引用针对哪个 ingest snapshot。
- 如果法律/版权允许保存 source snapshot，则设计 snapshot reference；否则至少保存 hash + ingest time。

B. Index / Dataset Consistency
- Vector/BM25/Graph/Chunk/Metadata index 必须记录 dataset_version。
- 启动时检查各 index 是否对应同一 snapshot。
- mismatch 不得静默运行成“部分新、部分旧”的混合状态。

C. Release / Rollback
- 新 index/version 上线前跑 regression。
- 支持保留上一稳定版本并回滚。
- feature flags 允许逐模块关闭。

D. Concurrency / State Isolation
- ResearchState 必须 per-request/per-conversation 隔离。
- 不能用可变全局对象共享 Ledger。
- SSE 客户端中断时要正确清理任务/资源。

E. ACL Interface
- 当前公共 Tech-DB 可以不启用权限过滤。
- 但 Retrieval API 设计不要让未来 ACL 无法插入。
- 若以后进入内部受限数据，ACL filter 必须在候选进入 Agent context 前执行。

======================================================================
最终总验收标准
======================================================================

以下任意核心项不满足，都不能宣称升级完成。

1. Retrieval
- [ ] Vector / BM25 / Graph 三路可独立工作。
- [ ] RRF 主要作为融合/候选层。
- [ ] 存在真正 content-aware Reranker。
- [ ] 单路强相关 outlier 不因过早 Top25 截断轻易丢失。
- [ ] Evidence Selector 在 Reranker 后工作。

2. Data / Evidence
- [ ] 核心 record 有 Evidence Metadata。
- [ ] synthetic/no-body summary 被明确标记且不可作为最终证据。
- [ ] 同源转载不会计成多个 independent evidence。
- [ ] Source Suitability 是 claim-aware，不是网站绝对分。
- [ ] Temporal 能区分 current/historical/superseded/future prediction。
- [ ] Entity alias 可 canonicalize。
- [ ] data/index version mismatch 可检测。
- [ ] evidence 可通过 content_hash/version 追溯。

3. Agentic Retrieval
- [ ] 简单题走 FAST_RAG。
- [ ] 复杂题可 decomposition。
- [ ] Planner 与 Generator 角色分离。
- [ ] Evidence Ledger 真正控制流程。
- [ ] Grader = Rule Engine + GLM，而非纯 LLM yes/no。
- [ ] Gap Analysis 生成 targeted query。
- [ ] 多轮 Retrieval 可运行。
- [ ] 每个新增 query 对应具体 unresolved gap。
- [ ] 研究 loop 有 anti-drift 和 query dedup。

4. Stopping / Abstention
- [ ] evidence sufficient 可提前结束。
- [ ] no-new-evidence 可主动停止。
- [ ] critical gap 连续无改善可停止。
- [ ] unresolved conflict 可停止并报告。
- [ ] SUPPORTED / PARTIALLY_SUPPORTED / UNSUPPORTED / UNVERIFIED 四态有效。
- [ ] “KB 没找到”不会被表述成“现实世界不存在”。
- [ ] 系统可明确说明“深度检索后当前 KB 仍不足”。

5. Conflict
- [ ] AGREE / CONTRADICT / DIFFERENT_SCOPE / VERSION_UPDATE 能区分。
- [ ] unresolved conflict 不会被偷偷合并成确定事实。
- [ ] conflict 可触发 targeted retrieval。

6. Generation
- [ ] Generator 基于 Evidence Package。
- [ ] self-reported claim 保留 attribution。
- [ ] prediction/opinion/analysis 使用合适不确定语言。
- [ ] Generator 不用预训练知识补最终 factual gap。
- [ ] Major Claim 全部经过 evidence mapping。

7. Citation
- [ ] 每个最终有效 citation 有 exact original evidence span。
- [ ] full_body 优先于 body。
- [ ] 找不到 span 不允许退回正文开头。
- [ ] Citation exact-span validity = 100%。
- [ ] Invalid citation displayed = 0。
- [ ] 支持 multi-span。
- [ ] Reference Card 显示 supports_claims。
- [ ] 核心 evidence phrase 可高亮。

8. Verification
- [ ] citation id / record id / span 存在性有 deterministic checks。
- [ ] numeric/unit/time 关键错误可确定性检查。
- [ ] GLM verifier 独立调用。
- [ ] verifier exception -> UNVERIFIED。
- [ ] Verifier error treated as PASS = 0。
- [ ] verifier 覆盖最终使用的核心 evidence，不再只因 cost 控制固定 Top5。

9. Safety
- [ ] Retrieved text 被视为 untrusted DATA。
- [ ] prompt injection 文档不能修改系统工具/策略。
- [ ] 如果未来接 ACL，可在 retrieval result 进入 Agent 前过滤。

10. Observability
- [ ] 每个请求有 trace_id。
- [ ] 可定位错误到 rewrite/router/retrieval/rerank/selector/ledger/grader/conflict/generation/citation/verifier。
- [ ] 每轮 research state 可回看。
- [ ] index/model/prompt/data version 可记录。

11. Evaluation
- [ ] 不再只看 Recall@25。
- [ ] 有 Retrieval/Rerank/Evidence/Agent/Conflict/Citation/Abstention/Answer 指标。
- [ ] SHOULD_ANSWER / SHOULD_PARTIAL / SHOULD_ABSTAIN 都有 gold cases。
- [ ] 历史 bad cases 可 replay。
- [ ] 重大改动必须跑 regression。

12. Engineering
- [ ] Feature flags 支持渐进启用和回滚。
- [ ] 新模块失败有明确 safe fallback。
- [ ] API 尽可能向后兼容。
- [ ] 不一次性重写旧系统。
- [ ] 每个 Ticket 至少有单元测试或集成测试。
- [ ] ResearchState 并发隔离。
- [ ] Index/Dataset/Metadata 版本一致性可检查。

======================================================================
给 Coding Agent 的逐票执行规则
======================================================================

每完成一个 Ticket，必须按以下流程收口，不允许只写代码就宣布完成：

1. 运行该 Ticket 的单元测试。
2. 运行相关 regression subset。
3. 保存 benchmark before/after。
4. 检查 trace 是否能解释新逻辑。
5. 检查 feature flag 关闭时旧路径是否仍可工作（若该功能适用）。
6. 检查异常路径是否 fail-safe。
7. 更新相关 schema/version/documentation。
8. 只有 Definition of Done 全部满足，才进入依赖它的下一个 Ticket。

最终架构原则：

“在 Tech-DB 固定知识库范围内，尽可能完整地找到高质量、相互独立、时间正确、可追溯的证据；只说证据真正能够支持的话；证据不足时继续有目的地寻找；搜索饱和后仍不足时，明确承认不足。”
